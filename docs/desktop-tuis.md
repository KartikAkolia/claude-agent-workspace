# Desktop TUIs: audio, display and webcam

`scripts/audio-tui.sh`, `scripts/display-tui.sh` and `scripts/webcam-tui.sh` are whiptail front ends for PipeWire/PulseAudio (through `pactl`), X11 displays (through `xrandr`) and V4L2 webcams (through `v4l2-ctl`). They were written for the keyboard-driven dwm desktop, to do from one menu tree what pavucontrol, arandr and guvcview would otherwise need a mouse for, and they share their helpers from `scripts/lib/tui.sh`. Run them from a terminal inside the graphical session as the desktop user. None of them needs or asks for root, and the display TUI needs an X11 session. Status: the audio and display TUIs were added on 2026-08-30 and the webcam TUI on 2026-09-11. All three were reworked in the [2026-11-14 script audit](script-audit-2026-11-14.md), but its fixes were verified only against stubs, never against real PipeWire, X or cameras (item 4 of its "Still needs Kartik" list). `scripts/test_tui_lib.py` covers the shared library, not the menus.

```bash
scripts/audio-tui.sh
scripts/display-tui.sh
scripts/webcam-tui.sh
python3 scripts/test_tui_lib.py -v
```

None of the three takes command-line arguments, so `--help` just starts the TUI.

## Shared library and conventions

`scripts/lib/tui.sh` holds the helpers in one copy, so a fix to dialog handling, error reporting or number parsing reaches every TUI at once. Each TUI looks for it beside its own real path (`readlink -f` on `BASH_SOURCE`), so a symlink to the script, in `~/.local/bin` for example, still works. A copy taken out of the checkout stops with `error: <dir>/lib/tui.sh is missing; run <script> from the repo checkout, or keep scripts/lib/ beside it`. `dirname` and `readlink` have to work before the library is loaded, which is why no `require_tools` list names them. The library isn't executable and isn't meant to be run. It has a bash shebang only so `list-lint-files.sh`, which finds shell files by shebang, lints it.

All three run under `set -uo pipefail` without `set -e`. whiptail exits 1 on Cancel and 255 on Esc, which is ordinary control flow here, checked at every menu, so a blanket `-e` would abort the whole TUI on a keypress. Cancel or Esc in a submenu goes back, and on the main menu it quits. Every action re-reads device state when it starts rather than trusting what an earlier screen showed. The audio and webcam main menus and their looping submenus reopen on the item last chosen (`--default-item`), so Enter repeats the last action instead of jumping to the first item. The display main menu always opens at the top.

Two bash pitfalls shape the code. Dialogs are never shown from inside a `while read ... done < <(...)` loop: lists are collected first and the loops only build menu items, so whiptail never inherits the process substitution as its stdin. Temp files for `--textbox` views are removed with a plain `rm -f` at the end of the function, not with `trap ... RETURN`. A RETURN trap set inside a function isn't scoped to it: it stays set and fires again when an enclosing function such as `main_menu` returns, where the local `$tmp` no longer exists, and under `set -u` that kills the script.

### The whiptail rule

Every dialog goes through `wt`, which adds `--backtitle "$PROG"` and sends each box to the right place. whiptail draws on stdout, and nearly every picker runs inside `$(...)`, so a display-only box drawn there would land in the caller's variable while whiptail waits for a key on a screen that looks frozen (audit TUI-2). So `wt` draws `--msgbox`, `--yesno`, `--infobox` and `--textbox` straight on `/dev/tty`. Boxes that return a choice (`--menu`, `--inputbox`, `--passwordbox`, `--checklist`, `--radiolist`, `--gauge`) stay on stdout, and every call site captures the choice with `3>&1 1>&2 2>&3`. That swap sends the drawing to the script's stderr and whiptail's answer, which it writes on stderr, into the capture, so keep a TUI's stderr on the terminal. To find the box type, `wt` scans its arguments up to the first box option, skipping the values of `--default-item`, `--title` and the four button-label options. A new value-taking option belongs in that skip list too. Never pass `--height` or `--width`: this whiptail (libnewt 0.52.25 here) has no such options and exits without drawing anything. Sizes are the positional numbers after the text, and the menus pass `0 0 0`.

### Helper contract

| Helper | Guarantee |
| --- | --- |
| `PROG` | Read-only, the running script's file name (`${0##*/}`), used as the backtitle. A script that sources the library mustn't have made `PROG` read-only already; `sync-root-gtk-theme.sh` sets a plain `PROG` with the same value. |
| `die MSG` | Prints `error: MSG` on stderr and exits 1. |
| `require_tools TOOL...` | Unless every tool is on `PATH`, exits through `die` naming all the missing ones at once. |
| `wt ARGS...` | Runs whiptail as described above and returns its status: 0 for OK or Yes, 1 for Cancel or No, 255 for Esc. |
| `pick_menu TITLE EMPTY [TAG ITEM]...` | With no items, shows `EMPTY` in a msgbox and returns 1. Otherwise shows the menu and prints the chosen tag without a newline. It returns 0 only for a non-empty choice and passes through whiptail's nonzero status on Cancel or Esc. Capture it with `x=$(pick_menu ...)` and leave the action on a nonzero status. |
| `run_or_report WHAT CMD...` | Runs `CMD` with stdout discarded and returns its status. On failure it shows `WHAT:` and the command's stderr (or `exit status N` if it printed nothing) in a msgbox, so the error isn't painted over by the next screen (audit TUI-13). Call it directly, never in `$(...)`, where a side effect such as `display-tui.sh` marking its cache stale would be lost. |
| `normalize_int V` | Prints `V` with leading zeros dropped if it's a decimal integer (`08` gives `8`, `-007` gives `-7`, `-0` gives `0`) and anything else unchanged (`0x10`). It only prints and never shows a dialog. Every typed or file-read number goes through it before use. Bash arithmetic rejects `08` as bad octal and aborts, and `v4l2-ctl` parses with `strtol(..., 0)`, so `0250` would set 168 (audit TUI-7). |
| `int_le A B` | Whether A is less than or equal to B, for decimal integers of any length already in `normalize_int` form. It compares strings by sign, then digit count, then 9-digit chunks, because `[` and `$((...))` are 64-bit and misread anything longer, so a huge typed number can't overflow a range check. It doesn't validate its input, so callers check the format first. |

### sync-root-gtk-theme.sh

`scripts/sync-root-gtk-theme.sh` uses the library for `--pick` only. Its `--check` and `--apply` run as root, and the library is a file the desktop user can write, so it's sourced only inside the `pick)` case arm. `--pick` itself refuses to run as root, and the root paths execute nothing but the script file. The sync script mustn't define its own `wt`, `die` or `require_tools`. Both rules are tested; [gparted-root-theme-fix.md](gparted-root-theme-fix.md) explains the trust model.

## audio-tui.sh

It needs `whiptail`, `pactl` and `jq`, and exits straight away if `pactl info` can't reach the sound server. It reads state with `pactl -f json list ...` through `jq` and makes changes with plain `pactl` verbs. It never calls `wpctl` or `pw-cli`, so on PipeWire it goes through the PulseAudio compatibility layer, the same path pavucontrol uses, and shows what pavucontrol shows. The menu sets the default output and input, moves one app's playback or recording stream to another device (pavucontrol's Playback and Recording tabs), adjusts volume and mute per device, switches card profiles and picks the active port of an output or input.

Monitor sources, a sink's "record what you hear" loopback, are offered alongside real inputs and tagged `[monitor]`. pavucontrol's default "All Input Devices" view shows them too, and hiding them would make it impossible to route a recording to one, for example to capture system audio. Card profiles that pactl reports as unavailable, such as an HDMI profile before a display is detected, are marked `[unavailable]`. Ports are marked `[plugged in]` or `[not plugged in]` from jack detection, since picking an unplugged port is otherwise a silent no-op. Most jacks can't detect anything, so "availability unknown" is left unmarked. Setting a card's profile to `off` is the clean, reversible way to disable an output you never use, such as HDMI with no monitor attached, without blacklisting a kernel module.

**Volume cap.** For hearing and speaker safety, no change made here raises a channel above 150% (`VOL_CAP_PCT`). "Set exact volume %" accepts 0 to 150. A trailing `%` and leading zeros are tolerated, and the bound is checked with `int_le`, so an absurdly long number is rejected rather than overflowed. "Up" can't use pactl's relative `+5%`, which has no ceiling (audit TUI-6). Instead `volume_up_capped` reads the raw per-channel values and sets absolute ones. Every channel rises by the same amount, so an L/R balance survives, and the step shrinks so the loudest channel stops exactly at the cap. Raw values are `pa_volume_t` units, where `PA_VOLUME_NORM` (65536) is 100%. The 5% step is rounded to 3277 rather than truncated, so ten steps from 100% land exactly on the cap. The values are matched to the channel count from `channel_map`, because pactl's JSON keys volumes by channel position and a map with a repeated position collapses two channels into one. If the counts disagree, every channel is set together to the loudest plus the step. A device already at or above the cap is left alone with a message. "Down" uses pactl's relative `-5%`. The menu shows each channel's percentage, joined only when they differ, plus the mute state, and "set" starts from the loudest channel's value. pavucontrol's slider tops out at `PA_VOLUME_UI_MAX` (commit `211f901` checked its source), defined as +11 dB in `pulse/volume.h`, which is about 153% on pactl's scale. So the cap sits just under pavucontrol's ceiling, and it's enforced on every path, "up" included.

Not built: a presets action that saves the default devices and card profiles to `~/.config/audio-tui/presets/<name>.conf` and replays them through the same pactl calls. It's waiting on a choice of file format, flat `KEY=value` or one pactl command per line.

## display-tui.sh

It needs `whiptail`, `xrandr`, `awk`, `mktemp` and `rm` (the last two for the layout view). It refuses to start when `XDG_SESSION_TYPE` is `wayland` and stops if `xrandr --query` fails. It covers what arandr can't: arandr has no refresh-rate control, and its layout editor is mouse-only. The menu turns on connected displays that are off (detect), shows `xrandr --query` (layout), sets resolution and refresh rate (mode), sets the primary display, places one display left of, right of, above or below another (position), mirrors one display onto another, turns a display on or off (toggle) and rotates one.

**One probe per action.** Every parser reads the text of a single `xrandr --verbose`, which `main_menu` loads (`xr_load`) in the main shell before each action, so the pickers the action runs in `$(...)` subshells all see the same text. A probe is slow, and on some panels it makes the picture flicker. `run_xrandr` marks the cache stale before every change, whether or not the change succeeds, since a failed call may still have changed something, and the next read probes again. A probe made inside a subshell is thrown away, so `enable_output`, which can run after detect has just turned another display on, reloads in the main shell first. The layout view runs its own `xrandr --query` instead.

**Modes come from `--verbose`, set by XID.** `xrandr --query` prints one line per mode name. One size can turn up under several names (an interlaced `1920x1080i`, a custom `1920x1080_60.00`), one name's line can repeat a rate when two timings round to the same value, and nothing marks interlace. `--verbose` lists every mode on its own with its XID, flags, real size and rate. It marks the current and preferred modes with `*current` and `+preferred` words, not the `*+` suffixes `--query` puts on rates, which broke the old rate parser (audit TUI-1). The rate menu merges modes that would look identical (same size, rate and kind) into one choice, so every choice maps to exactly one mode. That choice stands for the current mode if it's among them, else a preferred one, else the first. Rates carry `i` for interlaced and `d` for double-scan. The mode is then set with `--mode <XID>`. `--mode NAME --rate R` would make xrandr take the first mode of that name whose rate is nearest R, which needn't be the one picked, and a size's modes can go by other names entirely.

**Modes no output owns.** A mode made with `--newmode` and never `--addmode`'d is printed by `--verbose` after the last output, in exactly the same form as that output's own modes, so `--verbose` alone can't tell where the last output's list ends. The plain listing can: there an output's modes are grouped one line per name, and only the leftovers keep the `NAME (0xNN) ...` form. `xr_load` reads that listing with `xrandr --current`, which doesn't probe the outputs again, and keeps those XIDs in `XR_LOOSE` for `output_modes` to skip. `output_modes` loads the cache in its own shell before its pipeline, because a load inside the pipeline would set `XR_LOOSE` too late for awk.

**Turning a display on.** Every action that can turn an output on goes through `enable_output`. It uses the output's preferred mode (`--auto`) or a picked one and places it `--right-of` the display whose right edge is furthest right. With no relation, xrandr would put it at `+0+0`, on top of whatever is there. It uses the rightmost display rather than the primary because xrandr doesn't move other outputs aside, so "right of the primary" would land on any display already to its right. A connected display that's off may have just been plugged in or been turned off on purpose, so detect asks about each one. Afterwards it reports which were turned on, which failed and which were left off (audit TUI-5). Setting a mode on a display that's off asks the same question before going through `enable_output`.

**Transforms.** xrandr keeps an output's transform across mode and position changes. The transform may be a scale an earlier mirror left, or the user's own HiDPI scaling. So when mode or position changes an output whose matrix isn't the identity, the TUI asks before adding `--transform none`. That gives a unit matrix without filter, the state an output starts in; `--scale 1x1` would also pin the filter to nearest. An unreadable matrix counts as the identity, so nothing is cleared on a guess. `enable_output` doesn't touch transforms, on the basis that an output that's off reads as the identity and xrandr turns it on with that. Position doesn't pass `--auto`, which would reset the display to its preferred mode and rate (audit TUI-4).

**Mirror.** The mirrored display has to show the same area as the one it copies, and `--auto` would put it on its own preferred mode instead. If it has a mode of that size (by real size, whatever the mode is named), the TUI switches it to the one nearest its current rate. It also clears any transform without asking, since a mirror has to be 1:1 and a leftover scale would stretch it. Only when there's no such mode does it keep the display's mode and scale the other's area onto it with `--scale-from`, which replaces any transform. Rotation isn't copied, so mirroring a rotated display stretches it to fit.

**Toggle** won't turn off the last display that's on: that leaves a black screen, and getting the picture back means typing blind. No change has a revert timer, because whiptail has no timeout (audit TUI-11), so a mode the monitor can't show stays until it's changed back blind.

## webcam-tui.sh

It needs `whiptail`, `v4l2-ctl`, `awk` and `grep`, and stops if `v4l2-ctl --list-devices` fails. The menu shows camera info (device caps and every control, in a textbox), offers an exposure and focus quick setup, browses and edits every control the driver reports, resets all controls to driver defaults, and saves and applies named profiles. `v4l2-ctl` has no structured output, so everything is parsed with awk, grep and bash regexes from `--list-ctrls-menus`. Unlike `--list-ctrls`, it gives a control's current value and a menu control's options in one pass. The Canon 4000D bridge's picture settings are applied in the camera by `start-canon-webcam.sh -q` through gphoto2, not here; see [canon-4000d-usb-webcam.md](canon-4000d-usb-webcam.md).

Only capture nodes are offered. `v4l2-ctl --list-devices` lists every `/dev/videoN` of a camera, including metadata-only nodes such as the UVC metadata stream. So each node's own `Device Caps` block has to include Video Capture; the aggregate `Capabilities` line doesn't count, because it lists a sibling node's caps too. That block is tab-indented in `v4l2-ctl -D` output, so the parser doesn't anchor it at column 0.

**Control names differ by driver.** The quick setup resolves each logical control from a short candidate list, and the first name the camera reports wins. The candidates are `exposure_auto` or `auto_exposure`, `exposure_absolute` or `exposure_time_absolute`, `focus_auto` or `focus_automatic_continuous`, and `focus_absolute`. The C920 reports `auto_exposure`, `exposure_time_absolute` and `focus_automatic_continuous`, the names `scripts/c920-apply-settings.sh` sets, while the christitus.com C920 article uses `exposure_auto` and `focus_auto` (commit `1990ae8`). A camera with none of these names is pointed at the browse menu, which works from whatever names the driver reports.

**Editing.** Bools are toggled after a yes/no, and menu controls are picked from their options. `int` and `int64` values are typed, normalised with `normalize_int` and range-checked with `int_le`, so values up to a control's real int64 range are accepted and longer ones rejected, never overflowed. They're also checked against the step, since drivers may round or reject an off-step value; the C920's `focus_absolute` only takes multiples of 5. The step test reduces each side modulo the step first, because `value - min` can itself exceed int64. `check_int_value` takes the caller's variable by nameref, which resolves by name, so its locals are prefixed `civ_`; a plain local `val` would shadow the caller's. Other types (bitmask, string and so on) aren't editable here, and the TUI prints the `v4l2-ctl --set-ctrl` command to use instead. Controls flagged inactive, because their auto mode is on, are marked, since the camera ignores a value written to one then. The browse list reopens on the control just edited, not the first one, so a repeated Enter can't toggle the first bool by accident.

**Settling.** The C920 can accept a manual exposure, report it straight back, then drift off it a second or two later while its auto exposure is still settling after a mode switch (seen 2026-10-21: 250 became 156), which an immediate read-back misses. So the quick setup's exposure and focus items and the manual preset apply values through `set_ctrl_settled`; browse edits don't. `set_ctrl_settled` sets the value, reporting a failure. Then, up to three times, it waits 2 s, reads the value back and re-applies it if it moved, and warns if the camera keeps moving it. It skips the check while the control is inactive, since the value would never settle. Its status is 0 if the value held, 1 if the set failed, 2 if the camera kept moving it and 3 if it was set but the control is inactive. The presets turn those into notes. This is the TUI's side of the C920 fix; the plug-in and boot side, a udev rule that starts a retrying service, is in [logitech-c920-webcam.md](logitech-c920-webcam.md).

**Presets.** The manual preset ("stable") switches auto exposure to the menu entry containing "manual" and prompts for a fixed exposure value. It then turns continuous autofocus off and prompts for a fixed focus value, where 0 is infinity. The auto preset switches auto exposure to the first entry matching "aperture" or "auto" and turns continuous autofocus back on. Each preset ends with a summary that says "applied" only if nothing fell short (audit TUI-14). Otherwise it lists each control that couldn't be read, got no value, was rejected, failed to set, kept drifting or stayed inactive. The quick-setup menu reopens on the last action: when it jumped back to "stable", an Enter after "auto" switched exposure straight back to manual.

**Reset to defaults** quietly sets every int, int64, bool, menu and bitmask control to its driver default, then reports how many were reset and how many were skipped as read-only or rejected. It's the undo for anything else in the TUI.

**Profiles** are flat `name=value` files, one control per line, in `${XDG_CONFIG_HOME:-$HOME/.config}/webcam-tui/profiles/<name>.conf`. Blank lines and lines starting with `#` are ignored, and every value goes through `normalize_int`, so a hand-edited `0250` means 250. A control the camera doesn't accept is skipped and counted instead of aborting the load, so a profile can be applied to a different camera. Saving snapshots every int, int64, bool, menu and bitmask control. A profile name can't be empty or contain `/`, which would point into a missing subdirectory. It can't start with `.`, which the load menu's `*.conf` glob would hide, or with `-`, which whiptail would parse as an option. An existing profile is overwritten only after a yes/no that defaults to no. The snapshot goes to a `.save.XXXXXX` temp file beside the profile and is renamed into place only once complete, so a failed write never truncates an existing profile. The leading dot keeps a leftover, after a Ctrl-C say, out of the load menu. `mktemp` creates the temp file 0600, so before the rename it gets the mode a plain redirect would have under the current umask. A write failure or an empty snapshot saves nothing and says so (audit TUI-8).

Loading applies a profile in two passes, controls whose name contains `auto` first. A manual value written while its auto mode is still on is ignored, or rejected (commit `1990ae8` recorded the C920 refusing `focus_absolute` while autofocus was on), and drivers don't always list the switch first: the C920 lists `focus_absolute` before `focus_automatic_continuous`. After a 2 s pause, one settle pass re-applies any active exposure or focus value that has drifted. The summary counts applied, skipped and re-applied settings.

Not built: a preview action that runs `ffplay` or `mpv av://v4l2:<device>` in a terminal, so an exposure or focus change can be judged by eye. It's waiting on a choice of terminal emulator to launch.

## Tests

`scripts/test_tui_lib.py` checks the library's wiring and helpers without running any device tool. Run it as your normal user with `python3 scripts/test_tui_lib.py -v`. It needs Python 3.11 or later for `unittest`'s `enterContext`. Don't run it as root, because the sync-script tests rely on `--check` and `--apply` stopping at the root check. CI runs the same command in the "TUI shared-library wiring tests" step of `.github/workflows/lint-bash.yml`. All 8 tests passed on 2026-11-15.

The library tests check that `lib/tui.sh` defines `wt`, `die`, `require_tools`, `pick_menu`, `run_or_report`, `normalize_int` and `int_le` and sets `PROG`. They check that no TUI defines any function the library defines, or sets its own `PROG`; the function list is read from the library, so a helper added later is covered. They also check that each TUI computes `tui_lib` and sources it. Each TUI is then started, directly and through a symlink in a temp directory, with a `PATH` holding only `dirname` and `readlink`. The test expects exit 1 and exactly `error: missing required tool(s): ...`. That proves the library was found, and it stops the run before any whiptail, pactl, xrandr or v4l2-ctl call. The expected tool list per TUI is pinned in the test's `TUIS` table, so changing a `require_tools` line means updating it. A copy of a TUI outside `scripts/` has to fail naming the missing `lib/tui.sh`. Finally, a bash snippet sources the library with a stub `wt` and checks four helpers. For `pick_menu` it tries an empty list, a pick, an empty choice and Cancel. For `normalize_int` it tries `08`, `-007`, `-0`, `0250`, `0x10` and non-numbers. `int_le` is tested across the int64 boundary and with a 20-digit number, and `run_or_report` on success, on a failure with stderr and on a bare exit status.

The sync-script tests check that `sync-root-gtk-theme.sh` has no copy of `wt`, `die` or `require_tools`, and that every line sourcing the library sits inside its `pick)` case arm. Run against a marker library, `--check`, `--apply`, `--list` and `--help` must never source it, while `--pick` must, then stop for lack of whiptail. A missing library has to stop only `--pick`. These tests have no `sudo` or `whiptail` on `PATH`, so nothing privileged or interactive runs.

No repo test covers the menus or the pactl, xrandr and v4l2-ctl parsers. The audit's fixes to them were verified with stubs that aren't part of the repo.
