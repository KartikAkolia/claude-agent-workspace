# Technical & Behavioral Interview Prep

Sourced per `docs/personal-research-guidelines.md`. Interview *process shape* below is
observed/aggregated across candidate reports and third-party interview-prep sources
(GeeksforGeeks, IGotAnOffer, Interview Query) rather than a single official published
guide — flag this distinction to the user rather than presenting it as company-confirmed.
Google publishes online-assessment prep materials on its own careers site, but not one
unified "how our interview works" document, so treat the stage-by-stage breakdown below
as informed pattern, not verbatim policy.

## Typical large-tech-company SWE process shape (aggregated, e.g. Google-style, current
as of the 2026 research date)

1. Resume/application screen.
2. Online assessment(s) — often a coding assessment plus, at some companies, a
   behavioral/work-style survey.
3. Technical phone screen(s) — usually 1–2 rounds, 45–60 min each, focused on data
   structures & algorithms, video call with a shared coding doc (rarely a real IDE).
4. Onsite/virtual-onsite loop — typically 2–4 more technical rounds (coding, sometimes
   system design for senior roles) plus a behavioral round.
5. Debrief and offer.

Analysis (reasonable, not a verified constant): candidates commonly report investing
1–3 months of dedicated prep for a large-tech-company SWE loop specifically. Smaller
companies and non-SWE IT roles (support, sysadmin, IT project coordination) typically
have a shorter, less algorithm-heavy loop — don't apply the SWE-specific 1–3 month
figure to a help-desk or IT-support interview prep plan.

## What's actually being evaluated (general, cross-referenced across sources)

- Problem-solving process, not just the final answer — verbalize the approach, start
  from a working brute-force solution before optimizing, rather than going silent.
  - Practice this out loud, not just by reading solutions — mock explaining the approach
    is the actual skill being tested, and it's not exercised by silently solving a
    problem alone.
- Role-specific knowledge appropriate to the actual role (e.g., networking depth for a
  network engineer role, SQL/data-modeling depth for a data analyst role) — don't run a
  generic "LeetCode algorithms" prep plan for a role that isn't algorithm-heavy. Match
  prep depth to what the target role's own job posting and `role-requirements.md`
  actually call for.
- Collaboration/communication signal — how the candidate responds to a hint, handles being
  wrong, and works with the interviewer, not just raw correctness.

## Behavioral interview prep

- Use the STAR structure (Situation, Task, Action, Result) built from the user's own
  actual resume bullets and real work history — never invent a scenario or outcome the
  user didn't actually experience.
- Prep a small set (4–6) of real stories that each can flex to answer multiple common
  prompts (a conflict, a failure, a time under pressure, a time leading something) rather
  than memorizing one story per possible question.

## Non-negotiable when applying this

Don't fabricate a company's specific interview process for the user as if confirmed fact
— if the user names a real company/role, search for that company's own published
candidate-prep material first, and clearly separate "this company confirms X" from "this
is the generally observed pattern for similar roles."
